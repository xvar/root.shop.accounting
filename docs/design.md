# store-service — дизайн-документ

Статус: черновик v0.1 (кикофф), обсуждается с пользователем.
Ведётся здесь, чтобы подхватывать из любой сессии/машины.

## 1. Идея продукта

Сервис для небольших магазинов (ткани в метрах, пиво, одежда и т.д.):

- **Покупатель** (сайт + мобильное приложение): смотрит товары с остатками,
  резервирует товар, может отменить/вернуть резерв. Оплаты пока нет.
- **Администратор**: добавляет товары (фото/видео), редактирует остатки,
  подтверждает выкуп резерва (резерв → продажа, остаток списывается).

Это демо: сначала обкатываем на знакомых, дорабатываем, потом выводим на рынок.
Предполагается, что "коробку" в будущем будут клонировать и дорабатывать под
конкретных заказчиков (embedded/white-label) — отсюда требование к Docker и
к точкам интеграции с внешними системами (не реализуются сейчас, но
закладываются как расширяемые места — например, интерфейс/порт для будущей
синхронизации остатков или приёма заказов из внешней учётной системы).

## 2. Основные сущности (черновик)

- `Product` — артикул (SKU), название, описание, категория, единица измерения
  (шт/метр/кг), фото/видео, текущий остаток, цена (для демо — опционально).
- `StockMovement` — журнал изменений остатка (причина: приход, резерв,
  отмена резерва, продажа, ручная корректировка) — нужен для аудита и
  чтобы остаток всегда был производным/проверяемым значением.
- `Reservation` — резерв товара пользователем: количество, статус
  (active/cancelled/fulfilled/expired), TTL резерва (сколько держим бронь).
- `Order` / `Purchase` — подтверждённый администратором выкуп резерва.
- `User` — покупатель (аутентификация — TBD, скорее всего просто
  телефон/email + OTP для демо).
- `Admin` — сотрудник магазина, роль.
- `QrCode` — привязан к `Product` (для склада/печати) и к `Reservation`/`Order`
  (для покупателя, чтобы предъявить на выдаче).

## 3. QR-коды

- Для товара: короткий код на основе артикула (SKU) — QR должен быть
  маленьким/плотным, чтобы нормально печататься на принтере этикеток.
  → используем короткий алфавит (base32/base62) и короткую полезную нагрузку,
  не URL целиком, а короткий id, который резолвится на сервере/в приложении.
- Для заказа/резерва: QR на основе случайного id (не последовательного,
  чтобы нельзя было подобрать чужой резерв).
- Библиотеки: генерация — zxing (JVM/Android) или qrcode (backend, любой
  стек); сканирование — вопрос стека мобильного приложения (см. §5).

## 4. Нефункциональные требования

- Тесты (unit + минимум e2e на ключевые сценарии: резерв → подтверждение →
  списание остатка).
- Аналитика и стабильность (crash reporting) — приоритет: бесплатные тарифы
  на малых объёмах. Кандидаты: Sentry (free tier, backend + mobile),
  PostHog (free tier, продуктовая аналитика), Firebase Crashlytics
  (для мобилы, если стек это позволяет).
- Docker/Docker Compose — обязательно, т.к. предполагается клонирование
  "коробки" под заказчиков.
- Точки интеграции с внешними системами — закладываем интерфейсы
  (например, порт для будущего адаптера остатков/заказов), саму интеграцию
  не реализуем.

## 5. Стек (черновик — нужно подтверждение пользователя, см. §7)

- Мобила/веб: Kotlin Multiplatform (KMP) + Compose Multiplatform (CMP) —
  указано пользователем явно (Android/iOS/Web из одной кодовой базы).
- Backend: не зафиксирован. Естественный кандидат, чтобы делить код/модели
  с KMP-клиентами — Kotlin + Ktor (или Spring Boot), Postgres, Flyway/Exposed.
  Альтернатива — любой другой стек, если пользователь предпочитает.
- Хостинг демо: недорогой VPS (например Hetzner) либо PaaS с бесплатным
  тиром (Fly.io/Railway) — зависит от бюджета/предпочтений пользователя.

## 6. Дорожная карта (этапы)

1. **Техническая база (сейчас)**: репозиторий, хостинг/VPS, Docker,
   CI, базовый скелет backend + design doc. ← мы здесь.
2. **Разбивка по фичам** с документацией и схемами (ER-диаграмма, флоу
   резерва, флоу QR) — на уровне, понятном не-разработчику.
3. **Реализация фич**: backend API → потом кроссплатформенный клиент
   (KMP/CMP: Android/iOS/Web).
4. Демо знакомым → доработка по фидбеку → подготовка к выходу на рынок.

## 7. Открытые вопросы

Решено пользователем (2026-09-11, через Telegram):

- [x] **Репозиторий**: GitHub, личный аккаунт пользователя, пока в личных
      проектах (не организация). `gh` CLI на машине не установлен/не
      авторизован — создание удалённого репозитория и push потребует либо
      установки+авторизации `gh`, либо пользователь создаёт репозиторий
      сам через веб-интерфейс и присылает URL/добавляет remote.
- [x] **Backend-стек**: Kotlin + Ktor подтверждены явно (в дополнение к
      KMP/CMP для клиентов) — "всё на чём специализируюсь, чтобы проще
      понимать и контролировать".
- [x] **Docker**: подтверждён, именно ради переносимости "коробки"
      (будет своя БД и т.д.). Пользователь открыт к альтернативе, которая
      хорошо переносится и на больших объёмах уезжает в Kubernetes под
      балансировку — Docker Compose сейчас это не блокирует (контейнеры
      те же, что пойдут в k8s/k3s позже).
- [x] **VPS/хостинг**: старт — бесплатный тир, но пользователь открыт к
      недорогому платному решению, особенно если на нём можно разместить
      не только это демо, но и другие проекты. Рекомендация (см. §5.1)
      — Hetzner CX22, пользователь ещё не подтвердил.

## 5.1 Рекомендация по хостингу демо

Пользователь просил вариант "недорого, но чтобы можно было разместить
несколько проектов, а не только это демо":

- **Рекомендация: Hetzner CX22** (2 vCPU, 4 GB RAM, 40 GB SSD, ~€4.35/мес,
  x86_64). Один VPS + Traefik/Caddy как reverse proxy по доменам/поддоменам
  — под ним можно держать этот демо-контейнер и другие проекты
  одновременно. Надёжный провайдер, дешёвые managed-балансировщики и k3s
  разворачивается на той же машине, когда объём вырастет — путь до
  Kubernetes прямой, без миграции с ARM/другой архитектуры.
- **Альтернатива (бесплатно, но менее предсказуемо)**: Oracle Cloud Always
  Free — ARM Ampere A1, до 4 OCPU/24 GB RAM/200 GB диска, бесплатно
  навсегда (не только первый год). Минус — регистрация и захват "Always
  Free" ARM-инстанса печально известны capacity-ошибками при создании, и
  архитектура ARM64 (для Kotlin/JVM это не проблема, но стоит иметь в виду
  для любых бинарных зависимостей).

## 8. Организация агентов (после решения открытых вопросов)

- **Сбор требований** — агент/сессия, уточняющая детали фич и пишущая
  спецификации по каждой фиче в `docs/features/*.md`.
- **Кодеры** — по фичам/слоям (backend API, KMP shared, Android/iOS/Web UI).
- **Верификация** — ревью кода + прогон тестов перед мержем, отдельная
  роль/агент, не совпадающая с автором фичи.

Оркестрация стартует после этапа 1 (техническая база) и фиксации стека.
